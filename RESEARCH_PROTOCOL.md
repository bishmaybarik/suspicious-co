# Research Protocol

## Objective

Conduct a careful exploratory empirical study of the nested subsidiary
structures of major Indian parent companies.

The objective is to discover economically interesting and statistically
defensible patterns in:

- subsidiary counts;
- corporate hierarchy;
- ownership depth;
- geography and jurisdiction;
- parent-child relationships;
- cross-border ownership paths;
- intermediary jurisdictions;
- financial characteristics;
- heterogeneity across ultimate parent groups;
- recurring structural motifs;
- corporate complexity;
- temporal patterns, if dates permit;
- and other relationships contained in the data.

Do not restrict exploration to hypotheses explicitly supplied by the user.

## Input data

Research input:

~/.agent-inputs/suspicious-co/subsidiary_financial_variables_refined.dta

Dictionary:

~/.agent-inputs/suspicious-co/subsidiary_financial_variables_refined_data_dictionary.txt

Treat these files as immutable, read-only inputs.

Never overwrite or modify them.

## Language and interpretation

Unusual does not imply wrongdoing.

Do not describe a company, jurisdiction, entity, transaction, or ownership
structure as fraudulent, illegal, corrupt, tax-evasive, abusive, or improper
merely because it is statistically unusual.

Use language such as:

- unusual
- anomalous
- distinctive
- concentrated
- complex
- intermediary-heavy
- worthy of further investigation

Legal, regulatory, institutional, or tax interpretations require separate
external evidence.

## Empirical standards

Every substantive quantitative claim must be reproducible.

For important results record:

1. unit of observation
2. numerator
3. denominator
4. filters
5. treatment of missing values
6. treatment of duplicates
7. entity-level versus ownership-path counting
8. weighting method
9. relevant code
10. robustness tests

Investigate whether important findings are:

- driven by one parent group;
- driven by company size;
- generated by duplicate entities;
- mechanically caused by nesting;
- sensitive to missing observations;
- sensitive to weighting choices;
- sensitive to entity versus path definitions.

Run leave-one-parent-out checks when appropriate.

## Hierarchical data

Do not assume rows correspond to unique companies.

Determine the true structure first.

Strongly consider constructing:

- unique entity table
- parent-child edge table
- ownership-path table
- parent-jurisdiction table
- parent-level analytical table

Python should normally handle hierarchy, graphs, recursive structures,
network analysis and data engineering.

Stata may be used for descriptive statistics, regressions, robustness,
publication tables and econometric analysis.

Codex writes to:

research/codex/
src/codex/
outputs/codex/

Do not inspect the other agent's research during blind discovery.

## Research state

Each agent maintains:

research/<agent>/STATE.md
research/<agent>/DATA_AUDIT.md
research/<agent>/FINDINGS.md
research/<agent>/IDEAS.md

Candidate findings should receive identifiers.

Claude:
C-F001, C-F002, ...

Codex:
X-F001, X-F002, ...

For each finding record:

- result
- exact statistic
- denominator
- why it is interesting
- robustness
- mundane explanation
- data-quality explanation
- falsification test
- research-value score

## Git behavior

Agents must never:

- modify main
- merge a PR
- force-push
- rewrite published history
- delete another agent's branch
- modify another agent's worktree

The external controller handles commits and pushes.

At the end of every research increment write:

.agent_runtime/commit_message.txt

containing one concise commit subject describing what was accomplished.

Examples:

research(geography): map jurisdiction concentration by parent

research(network): construct ownership paths and transition matrix

research(financials): compare financial weight across ownership depth

Also update STATE.md before ending the increment.
